Why this decision

Learning from an earlier, real failure

An earlier build in this same body of work put a 3-model FastAPI service on a free-tier host with a measured out-of-memory failure (512MB limit, ~695MB actual footprint). Two "obvious" fixes were tried and measured — both made things worse, not better:

Mitigation triedResult
bfloat16 weight loading998MB (worse than 695MB baseline)
Dynamic int8 quantization1024MB (worse still)

This capstone applies that lesson directly: deploy the model that's small by architecture, not by attempted compression after the fact.

Engineering

Challenges & how they were resolved

  • A silent, non-obvious data bug: 533 rows (~2.9%) of the source dataset carried the literal placeholder text "empty", not caught by a null check — found only by reading actual misclassified examples from the first training run, then fixed at the source.
  • Vite's static output vs. a fixed `/static` mount: the built frontend emits root-relative asset paths, so the backend mounts the built directory at / with html=True instead of a fixed /static prefix, discovered and fixed before it ever reached production.
  • Real system resource contention: DistilBERT fine-tuning ran under heavy concurrent load on the same machine — diagnosed directly via uptime/free -h rather than assumed to be a bug, and handled by patient background waiting.
Wrap-up

Lessons learned

  • A "correct" model and a "deployable" service are different properties — verify both.
  • A quick manual check can mask a bug a full run then surfaces — the placeholder-text bug proved that twice in one internship.
  • The best defense against a repeated mistake is designing the next system around the measured constraint, not just remembering it happened.
